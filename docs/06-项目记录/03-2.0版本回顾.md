**关键洞察**：代码量几乎翻倍，但这不是简单的功能堆砌。2.0 的增长主要分布在三个方向：

1. **多用户系统**（~15%）：从单人模式升级为多用户+注册+登录+切换
2. **视觉个性化系统**（~35%）：主题运行时引擎、氛围特效、背景/音乐/轮播
3. **编辑器体验深度打磨**（~25%）：Notion 风格写作空间、大纲、块菜单、源码模式

## 三、数据库层：从单人到多人

### 3.1 Schema 变化

```diff
+ model User {
+   id           String   @id @default(cuid())
+   username     String   @unique
+   passwordHash String
+   displayName  String   @default("")
+   avatar       String?
+   lastLoginAt  DateTime?
+   createdAt    DateTime @default(now())
+   updatedAt    DateTime @updatedAt
+   entries      Entry[]
+ }

  model Entry {
    ...
+   userId    String
+   user      User      @relation(fields: [userId], references: [id], onDelete: Cascade)
    ...
+   @@index([userId])
  }
```

### 3.2 决策变更

**D-006 被推翻**。原决策："MVP 不实现用户系统、登录、权限。项目为单用户设计。"

2.0 中实现了完整的：
- 用户注册/登录（bcryptjs 密码哈希）
- Session Cookie（httpOnly + secure）
- Middleware 全局路由保护
- 多用户切换
- 头像系统
- 草稿箱（多用户隔离）

这是 **2.0 最大的架构级变更**。从"单人本地工具"升级为"多用户网络应用"。这一变更驱动了 6 个新 API 路由、1 个新数据库模型、以及整个认证中间件。

## 四、核心功能模块变化

### 4.1 编辑器（变化最大）

| 功能 | 1.0 | 2.0 |
|------|-----|-----|
| 基础格式化 | H2/H3, Bold, Italic, List, Quote, HR | **H1-H5 全部**、加粗、斜体、**下划线**、**删除线**、行内代码 |
| 特殊块 | Callout, Divider | Callout, Divider, **代码块（多语言语法高亮）**、**任务列表** |
| 链接 | window.prompt 弹窗 | **编辑器内浮层 Popover** |
| 块菜单 | 无 | **悬停 `+` 按钮** — 完整块类型选择 |
| 大纲 | 无 | **侧边栏大纲**（H1-H5 自动生成，可点击跳转） |
| 快捷键 | Ctrl+B/I/Z/Y/S | **20+ 快捷键**（对标 Notion/飞书） |
| 草稿 | localStorage 单草稿 | **草稿箱**（多草稿 + localStorage + 800ms debounce） |
| 字数统计 | 无 | **右下角固定词数+阅读时间** |
| 源码模式 | 无 | **可视化/源码双模式切换** |
| 粘贴 | 基础文本 | **Ctrl+V 图片粘贴、拖拽上传** |
| 数学公式 | 不支持 | **KaTeX 行内 `$` + 块级 `$$`** |
| Mermaid | 不支持 | **Mermaid 图表渲染** |
| 编辑器布局 | 窄编辑区 + 常驻工具栏 | **宽编辑区（可自定义页宽）+ hover 显隐工具栏 + relative 定位** |

| 色彩模式 | Light/Dark/System | Light/Dark/System + **主题色自定义（12 预设 + 色盘）** |

| 视频背景 | 不支持 | **支持** |
| 页面横幅 | 基础图片 | **飞书式拖拽定位 + 高度设置 + 边界选项** |
| 轮播图 | 无 | **20 张轮播图 + 渐变平滑过渡 + 立体阴影** |
| 背景音乐 | 8 首基础播放 | **16 首曲目** + 模式切换（单曲/列表/随机循环）+ **音乐可视化** |
| 氛围特效 | 无 | **花瓣/光尘/飘雪/落雨/几何** + 鼠标跟随 |
| 字体/间距 | 固定 | **字体选择 + 字号滑块 + 行间距 + 模块间距 + 段落间距** |

### 4.3 时间与氛围系统（全新）

2.0 新增了一套 **Theme Runtime Engine**：
- 时间驱动：根据系统时间自动切换日间/夜间主题
- 天气驱动：天气组件联动主题氛围
- 场景主题：季节感知（春樱/夏园/秋暖/冬月）
- 生态系统：ecosystem 模块（config + events + scheduler + garden-ecosystem）为未来的动态内容生长提供基础设施

## 七、逻辑关联：功能模块之间的协同

### 7.1 主题运行时引擎的联动网络

```
Theme Runtime Engine
    ├── 时间 (daytime-theme) ──── 自动切换日/夜色彩模式
    ├── 天气 (weather-widget) ─── 影响氛围特效选型
    ├── 主题 (scene-themes) ──── 联动背景 + 音乐 + 动效 + 主色调
    │       ├── 背景 (background-provider)
    │       ├── 音乐 (audio-provider)
    │       └── 动效 (ambient-provider)
    └── 生态 (garden-ecosystem) ─ 定时调度 + 事件驱动
```

这是 2.0 最精妙的设计：切换一个主题（如"星空"），会自动：
1. 更换背景图为星空夜景
2. 切换到暗色模式
3. 播放特定的背景音乐
4. 启用对应的氛围特效
5. 更新主题色

### 7.2 用户系统的贯穿链路

```
User Model (Prisma)
    ├── auth.ts ───────── 会话管理 + 密码哈希
    ├── middleware.ts ─── 全局路由保护
    ├── API Routes ───── 注册/登录/切换/删除/头像
    ├── nav.tsx ──────── 头像展示 + 账号切换 UI
    ├── avatar-editor ── 头像编辑
    ├── Entry ────────── 所有内容关联 userId
    └── Drafts ───────── 草稿按用户隔离
```

### 7.3 编辑器的体验闭环

```
Editor (tiptap-editor)
    ├── block-menu ────── 悬停 "+" → 块类型选择 → 插入
    ├── shortcuts ─────── 20+ 快捷键 → 无需抬手
    ├── toc-highlighter ─ 大纲实时同步 → 点击跳转
    ├── source-mode ───── 可视化 ↔ 源码双模式
    ├── drag-handle ───── 拖拽排序

    ├── mermaid ───────── Mermaid 图表
    └── font-size ─────── 字号自定义
```

### 7.4 生态系统模块的"超前设计"

`ecosystem/` 模块在 2.0 中已搭建了完整的事件-调度-配置体系，但目前仅用于氛围特效的定时切换。这是为 3.0 的"数字生命"概念预留的基础设施，当前利用率为 **~10%**。

## 八、不足与缺点分析

### 8.1 架构层面

#### 🔴 D-006 被推翻但未更新决策文档

原决策 D-006 明确"MVP 不实现用户系统"。2.0 实现了完整的多用户系统，但 `DECISIONS.md` 中 D-006 未追加"D-006 被推翻"的记录。这在审计追溯上留下了缺口。

#### 🔴 D-009 的半推翻

原决策"不使用第三方 UI 库"，但 2.0 引入了 `swiper`（轮播图）。虽然是功能性依赖而非 UI 组件库，但边界模糊。

#### 🟡 生态系统模块过度设计

`ecosystem/` 的 4 个文件定义了完整的事件总线、调度器、配置系统，但当前实际使用场景极少。这是典型的"为未来设计"，增加了维护负担。如果 3.0 不使用这套系统，它将成为死代码。

#### 🟡 Server Actions 与 API Routes 的混合

原决策 D-007 "MVP 全部使用 Server Actions"，但 2.0 引入了 9 个 API Route。虽然这些路由主要用于认证（Auth.js 模式的自然需求），但导致了两种数据流模式的混合——部分功能用 Server Actions，部分用 REST API。对新开发者不够友好。

### 8.2 功能层面

#### 🔴 空壳功能

多个 UI 入口对应的功能未完整实现：
- 块菜单中部分选项点击无反应
- Mermaid/公式在某些边界情况下不可用
- 页面横幅的高度设置无效
- Live2D 模型更换无效

#### 🔴 选中文本弹出菜单功能不足

目前选中文本后弹出的工具栏只有加粗、斜体、下划线等少数几个选项，远少于 `+` 块菜单的功能。用户需要"选中一段文字 → 将其转为 Callout/引用/代码块"的能力。

#### 🟡 循环播放 bug

音乐播放器存在"进入页面后只播一遍就停"和"点击当前曲目不播放"的问题，音乐系统的可靠性不足。

#### 🟡 设置项孤岛

部分设置项（如模块间距、段落间距）因组件内部样式写死而无法生效。这会导致用户在设置页调整后看不到效果，产生"设置页坏了"的感知。

#### 🟡 草稿箱与自动保存的交互不清

自动保存（800ms debounce → localStorage）和草稿箱（多草稿管理）是两套独立的机制，它们之间的交互逻辑（何时覆盖、何时新建草稿）对用户不够透明。

### 8.3 代码质量层面

#### 🟡 存在备份文件

`src/app/plant/page.tsx.bak` 留在源码目录中，应该在重构完成后删除。

#### 🟡 CHANGELOG 断更

`CHANGELOG.md` 在 P2.1（2026-05-31）之后停止更新。后续 15+ 个 commit 的重要变更（主题运行时、氛围系统、伴聊、编辑器重构等）未记录。这违反了项目自身的 BUILD_RULES.md 规范。

#### 🟡 快照系统停用

`snapshots/` 目录在 Phase 1 之后未再创建新快照。"一快照一 Commit"规范在 2.0 开发中被放弃。

### 8.4 体验层面

#### 🔴 内容为空的根本问题未解决

`PRODUCT_CHECKPOINT_04.md` 指出"最大短板：内容为空"。2.0 添加了大量功能，但这个根本问题依然存在——测试数据不说话，花园还没有被真正种植。

#### 🟡 功能蔓延导致的认知负担

1.0 的 Settings 页面只有主题切换。2.0 的 Settings 页面包含了背景、音乐、主题、氛围、字体、布局、Live2D、AI 等十多个设置区域。这种"设置页爆炸"对用户是一种认知负担。

#### 🟡 性能隐患

新增的粒子特效、视频背景、音乐可视化、Live2D 渲染同时运行时，对性能的影响未经过系统测试。

## 九、对 3.0 的展望

### 9.1 应该优先做的事

#### 优先级 A：填坑（Debt Repayment）

1. **激活空壳功能**：块菜单中的所有选项都应有实际效果。Mermaid/公式需要可靠的渲染管线。
2. **修复音乐系统**：循环播放、点击切换、与设置页联动——这三个 bug 直接影响日常使用体验。
3. **完善选中文本菜单**：对标飞书的"选中即显工具栏"，补充块类型转换能力。
4. **更新 CHANGELOG**：补录 2.0 后半段的变更记录。
5. **清理死代码**：删除 `page.tsx.bak`，评估 `ecosystem/` 是否保留。

#### 优先级 B：做减法（Simplification）

1. **设置页重构**：将十多个设置区域收敛为 4-5 个选项卡（外观/编辑器/音频/关于），降低认知负担。
2. **合并自动保存与草稿箱**：统一为一套"内容暂存"机制，对用户透明。
3. **移除无效设置项**：如果模块间距因组件写死而无法调整，要么修复实现，要么从设置页移除。

### 9.2 应该推进的 Phase 6-7

按照 ROADMAP，下一个应该推进的阶段：

#### Phase 6：历史版本（建议 3.0 核心目标）

> 让内容永不丢失。

- 自动快照（每次保存自动创建版本）
- 版本列表（可查看所有历史版本）
- 版本比较（diff 视图）
- 一键回滚

这是当前最缺失的"安全感"功能。用户需要知道"改坏了还能回去"。

#### Phase 7：知识关联（建议 3.0 次要目标）

> 在内容自然增长后形成连接。

- Wikilink `[[ ]]` 解析器
- Backlinks 面板
- 关联推荐

但前提是用户已经有足够多的真实内容。如果花园还是"空"的，关联系统就无意义。

### 9.3 应该重新审视的决策

| 原决策 | 当前状况 | 建议 |
|--------|---------|------|
| D-006 单人模式 | 已实现多用户 | 追加"后记：D-006 在 2.0 中被推翻" |
| D-007 Server Actions 优先 | 混用 API Routes | 明确规则：认证用 API，数据操作用 Server Actions |
| D-009 无第三方 UI 库 | 引入 swiper | 记录并接受，或寻找替代方案 |
| 快照系统 | 停用 | 要么恢复执行，要么正式废弃并更新 BUILD_RULES.md |

### 9.4 3.0 的核心理念建议

**从"功能驱动"转向"内容驱动"。**

2.0 的发展模式是"用户提需求 → 实现功能"。这导致了功能蔓延和部分空壳。3.0 应该切换为：

> 先种花（真实使用积累内容）→ 花告诉我们需要什么 → 再建造工具

具体而言：
- **少做新功能，多做"内容感知"**：让花园能根据用户已有的内容提供洞察
- **深耕编辑器体验**：这是用户每天接触的界面，比任何新功能都重要
- **完成 AI 园丁（Phase 5）**：在积累足够内容后，AI 摘要/标签建议/回忆关联的价值才能真正体现
- **考虑数据可移植性**：Markdown 导出已实现，但导入（从 Obsidian/Notion/飞书迁移）是一个高价值但未讨论的功能

## 十、总结语

### 数字花园 2.0 是一个什么样的产品？

它是一个 **"功能丰富到超出预期，但细节打磨仍需时间"** 的私人数字空间。

### 做对了什么

1. **编辑器体验大幅提升**：Notion 风格写作空间、20+ 快捷键、大纲导航、块菜单——这些让写作从"能用"变成"愿意用"
2. **主题联动系统设计精妙**：切换一个主题，背景/音乐/动效/色彩全部联动，这种"一键换境"的体验是 2.0 最亮眼的创新
3. **视觉氛围系统的完整性**：从 CRT 效果到樱花飘落，从音乐可视化到天气组件，每个细节都在强化"这是我的空间"的感觉
4. **开发速度惊人**：11 天内完成 47 个 commit，从项目初始化到完整的全栈应用

### 做得不够好的

1. **空壳功能**破坏了信任——用户点击一个按钮期望功能生效，但什么都没发生
2. **功能蔓延**导致"设置页爆炸"和部分功能半成品
3. **工程纪律松懈**：CHANGELOG 断更、快照停用、备份文件未清理
4. **"内容为空"的根本问题**被功能开发所掩盖

### 对 3.0 的一句话

> **3.0 应该成为"花园真正开始生长"的版本——少建工具，多种花。**
