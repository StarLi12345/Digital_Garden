# Background System Review 01

> 背景图系统设计审查
>
> 核心问题：一张图如何让花园从"工具"变成"我的空间"？

---

## 第一部分：为什么背景图比主题更重要

### 用户心理

**主题是"设置"。背景是"选择"。**

切换主题（Light → Dark → Moonlit）是一种"配置行为"。用户在做一次理性的、功能性的切换——"现在是晚上，我应该用暗色。"这和切换手机亮度没有本质区别。

选择背景图是"表达行为"。用户在说："这张图让我平静。""这张图是我喜欢的东西。""这个空间开始有我的痕迹了。"

| 维度 | 主题 | 背景图 |
|------|------|--------|
| 用户行为 | 配置（理性） | 选择（感性） |
| 身份表达 | 弱——"我用暗色模式" | 强——"这是我的花园" |
| 感知速度 | 需要对比两个主题才能感知差异 | 一眼看到 |
| 更换频率 | 低频（可能永远不换） | 中频（随心情、随季节） |
| 情感依附 | 低 | 高——用户会对"自己的背景图"产生情感 |

### 产品人格

Digital Garden 的隐喻是"推开自己的房门"。

主题是"房间的墙色"。背景图是"房间里的窗"。

墙色影响氛围——暖色温馨，暗色沉静。但没有人会因为朋友家的墙色好看来做客。人们会因为朋友家的窗景好看来做客。

**背景图 = 花园的窗。透过它，用户看到自己选择的世界。**

### 长期使用场景

用户使用花园 6 个月后：
- 主题可能从未切换过（默认花园主题一直用）
- 但背景图会被多次更换——春天用樱花图、夏天用海边图、秋天用红叶图
- 更换背景图是用户与花园之间最简单的"互动仪式"——不需要写东西，只需要告诉花园"今天我想看到这个"

### 日记/花园类产品特点

Day One（日记应用）不支持自定义背景。它用纯色背景。这很克制——但它也因此缺少"我的空间"的感觉。

Are.na 支持频道封面图。一张封面图让一个频道从"分类"变成"房间"。

Digital Garden 介于两者之间：比 Day One 更个人化，比 Are.na 更私人。背景图是让花园有"房间感"的最轻量方式。

## 第二部分：资源库审查

### 建议分类

基于资源库 168 张图片的实际内容（Pixiv 插图、东方 Project、摄影、截图）：

| 分类 | 情绪 | 适配主题 | 预估数量 |
|------|------|---------|:--:|
| **Garden** | 温暖、自然、阳光 | 花园 | ~30 |
| **Moonlight** | 夜晚、星空、安静 | 月夜 | ~20 |
| **Sakura** | 粉色、季节、柔软 | 樱庭 | ~25 |
| **Rain** | 雨天、静谧、沉思 | 花园/月夜 | ~15 |
| **Memory** | 怀旧、电影感、胶片色 | 月夜 | ~15 |
| **Anime** | 二次元插图、东方、Pixiv | 全部 | ~50 |
| **Library** | 书、咖啡、安静室内 | 月夜 | ~10 |
| **Other** | 无法分类 | — | ~10 |

### 推荐目录结构

不在 `resource/` 内重组（尊重用户现有文件组织）。而是在应用层建立分类映射：

```
src/lib/backgrounds.ts  ← 分类映射文件（非 resource/ 内）
```

```typescript
// 伪结构：不移动用户文件，仅在配置中建立分类
const BACKGROUND_CATEGORIES = {
  garden:   ["resource/picture/xxx.jpg", "resource/picture/yyy.png"],
  moonlight: ["resource/picture/zzz.jpg", ...],
  sakura:   [...],
  rain:     [...],
  memory:   [...],
  anime:    [...],
};
```

**原则**：
- 不移动、不重命名、不修改用户的 resource 文件
- 背景系统只引用现有文件路径
- 用户未来可以自行向 resource 添加图片，背景系统自动识别

## 第三部分：背景系统 MVP

### ✅ 属于 MVP

| 能力 | 说明 |
|------|------|
| **从 6 个预设背景中选择** | 每个分类提供 2-3 张精选图片作为预设 |
| **无背景（默认）** | 保持当前纯色背景，向后兼容 |
| **localStorage 持久化** | 用户选择的背景在刷新后保持 |
| **主题适配** | 不同主题下有不同默认背景推荐 |
| **背景预览** | 在 Settings 页预览背景效果 |

### ❌ 推迟到 V2+

| 能力 | 原因 |
|------|------|
| 上传自定义背景 | 需要文件上传组件、存储管理、格式校验。属于 Phase 3 |
| 视频背景 | 性能、流量、与安静气质冲突。永久不做 |
| 云同步背景设置 | 需要后端。Phase 4+ |
| 背景自动轮换（每日/每打开） | 有趣但有侵入性——用户可能在某一天不喜欢被分配到的背景 |
| 背景市场/社区分享 | Digital Garden 不是社交产品。永久不做 |
| AI 生成背景 | 不需要。用户有自己的图片 |

### MVP 范围 = 1 句描述

**从 6 个分类中各选 2-3 张精选图片作为预设背景，用户在 Settings 页选择和预览，选择持久化到 localStorage。**

## 第四部分：阅读体验评审

这是整个背景系统设计中最重要的问题。

### 问题

背景图是覆盖整个页面的。而花园的核心是**文字内容**——用户需要清晰、不费力地阅读。

一个高对比度、色彩丰富的背景图会让文字难以辨认。

### 方案对比

#### 方案 A：全局遮罩（Overlay）

```
┌──────────────────────────┐
│  半透明遮罩层（#000/40%）  │
│  ┌────────────────────┐  │
│  │  卡片（bg-card）     │  │  ← 内容区域有实色背景
│  │  文字清晰可读        │  │
│  └────────────────────┘  │
│                          │
│  背景图（底层）           │
└──────────────────────────┘
```

**优点**：文字区域有实色背景保护，背景图只出现在"间隙"中
**缺点**：叠加两层——背景图 + 遮罩 + 卡片——可能显得重

#### 方案 B：模糊层（Blur）

```
┌──────────────────────────┐
│  模糊背景图（blur: 40px）  │
│  ┌────────────────────┐  │
│  │  卡片（bg-card/90%） │  │  ← 半透明卡片，透出柔和的背景色
│  │  文字清晰可读        │  │
│  └────────────────────┘  │
└──────────────────────────┘
```

**优点**：背景图的色调透过卡片——温暖但不抢眼
**缺点**：CSS `backdrop-filter: blur()` 有一定性能消耗

#### 方案 C：仅页面背景（Page Background Only）

```
┌──────────────────────────┐
│  背景图（页面背景）        │
│                          │
│  ┌────────────────────┐  │
│  │  卡片（bg-card）     │  │
│  │  纯色不透明          │  │
│  └────────────────────┘  │
└──────────────────────────┘
```

**优点**：最简单。卡片完全遮挡背景，阅读零影响
**缺点**：背景图只在卡片周围可见——在大屏幕上（> 1200px）效果好，在小屏幕（卡片撑满宽度）上背景图几乎不可见

### 推荐方案：C（页面背景）+ 可选 A（遮罩）

**MVP 采用方案 C**：

- 背景图作为 `<body>` 的 `background-image`
- 所有内容卡片保持 `bg-card` 纯色（不透明）
- 背景图只在页面两侧和卡片间隙可见
- 在小屏幕上（卡片撑满宽度），背景图自动退居——不干扰阅读

**V2 可选方案 A**：

- Settings 中增加"背景透明度"选项
- 用户可选择让卡片半透明（`bg-card/90%`），背景图更可见
- 默认保持不透明（文字安全）

### 为什么不是方案 B

模糊层的性能消耗在低端设备上可能明显。且模糊后的背景图为内容提供的"环境感"价值降低。**当前阶段优先保证阅读安全和性能。**

## 第六部分：移动端评审

### 性能

- 一张 1920×1080 的 JPEG 背景图：~200-500KB
- 首次加载时作为 CSS background-image 异步加载——不阻塞页面渲染
- 使用 `background-image` 而非 `<img>` 标签——浏览器自动优化
- **结论**：可接受。200KB 的图片在现代网络条件下 < 0.5s

### 流量

- 用户选择背景后，图片路径存入 localStorage
- 每次打开页面时加载同一张图——浏览器缓存
- 用户切换背景时才加载新图
- **结论**：可接受。一次加载，缓存复用。

### 可读性

- 移动端屏幕窄（375px），卡片撑满宽度
- 背景图在卡片两侧几乎不可见
- 这意味着移动端的背景图价值有限——但它也不干扰阅读
- **结论**：移动端背景图是"微弱的存在感"，不影响可用性。

### 电量

- CSS `background-image` 不消耗额外电量（纯渲染，无动画）
- 不像视频背景或粒子效果
- **结论**：无影响。

### 建议

- 移动端默认使用同一背景配置（不单独处理）
- 未来可考虑移动端自动关闭背景（减少流量），但 MVP 不做

### 状态管理

- localStorage key: `garden-background` — 存储用户选择的背景路径
- 如果 localStorage 为空 → 无背景（默认纯色）
- 使用时在 `<body>` 上设置 `style={{ backgroundImage: url(...) }}`
- 不需要状态管理库，不需要 Context

### 是否需要数据库

**不需要。** 背景选择是纯本地设置，不需要持久化到 Prisma。

### 是否需要新增依赖

**不需要。** 纯 CSS background-image + localStorage + React state。

### 预计代码量

| 文件 | 行数 |
|------|:--:|
| `src/lib/backgrounds.ts` | ~40 行 |
| `src/app/globals.css` | ~10 行 |
| `src/app/layout.tsx` | +5 行 |
| `src/app/settings/page.tsx` | +50 行 |
| **总计** | **~105 行** |

### 预计风险

| 风险 | 缓解 |
|------|------|
| 图片路径错误（文件不存在） | `onerror` 回退到无背景 |

| 移动端卡片撑满导致背景不可见 | 接受——移动端背景图是微弱存在感，不破坏体验 |

## 最终问题：用户第一次打开应看到什么

**什么背景都没有。**

不是 Garden。不是 Moonlight。不是 Sakura。

是纯色背景。和现在一样。

因为：

1. **默认无背景是正确的默认。** 花园在用户没做任何选择之前，不应该替用户决定"I think you'll like this"。它应该是空白的，等待被填充——就像刚搬进的新房间。

2. **背景是用户主动添加的。** 当用户在 Settings 中第一次看到背景选择器——"哦，我可以选一张图作为背景"——然后选了一张。从那一刻起，这张图不是系统预设的，是**用户自己选的**。

3. **"我的花园"不是第一次打开就产生的。** 它产生于用户为花园做的每一个微小决定——第一张背景图、第一条标签、第一篇被 Callout 标记的文字。空白是花园给用户的第一个尊重："你的空间，你来填。"

---

> **背景系统的目标不是让花园更好看。**
>
> **是让用户说："这张图是我选的。"**
