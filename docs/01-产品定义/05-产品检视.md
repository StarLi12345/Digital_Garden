# Product Checkpoint 04 — Experience-driven Review

> 不是"还缺什么功能"。是"我已经用了 30 天吗，我会继续用吗"。

---

## 1. 连续使用 30 天，最可能坚持使用的功能

**"来自花园"（随机回忆）。**

不是因为它是技术上最好的功能。是因为它是唯一不需要用户主动决策的功能。

其他所有功能——创建、编辑、搜索、筛选、标签——都需要"我想做什么"的意图。来自花园不需要。打开首页，它就在那里。看一眼。有时候是惊喜，有时候是无感，但一个月后，那些"惊喜"的瞬间会沉淀为对花园的情感。

排名第二：**时间视图**。不是因为用户每天看它，而是因为半年后回头看，看到"2025年12月 · 3条"——那个月刚开始用。时间维度是花园最独特的叙事。

排名第三：**创建流程本身**。自动保存 + 类型选择 + 标签。不是因为这三个功能好，而是因为它们组合成了一个流畅的"写一条记录"的闭环。不需要想"怎么用"——打开 /plant，写，关闭。草稿还在。

---

## 2. 看起来很好但实际使用频率很低的功能

**"本月你的花园"（类型聚合）。**

设计评审时我给它排了很高的优先级——"让花园第一次说出关于用户的话"。但实际使用中，它的位置尴尬：在统计卡片和来自花园之间，用户看一眼数字，看一眼类型分布，然后眼睛直接跳到"来自花园"。

类型聚合的问题是：它需要用户**停下来阅读和分析**。而用户在首页的行为是**快速扫描**。"来自花园"只需要一瞥——"哦，5 个月前的记录"。"本月你的花园"需要读 4 行数字和一句话的总结。认知成本高出 3 倍，停留时间未必多 30%。

**Divider** 也是。有价值，但在"需要时才出现"的那一瞬间。它不构成每天的使用体验。

**Blockquote**。引用别人的话——在个人日记中，这真的很少发生。Callout（"我自己说的话值得标记"）的使用频率预计是 Blockquote 的 3-5 倍。

---

## 3. 当前编辑器最影响写作流的地方

**有两个。一个明显，一个深层。**

**明显的**：Link 的 `window.prompt`。在流畅的键盘输入中，突然弹出一个浏览器原生对话框——这是整个产品中最不"花园"的交互。它不像便签、不像回忆、不像任何温暖的东西。它像一个 1998 年的网页。

**深层的**：从键盘切换到工具栏再回到键盘的"上下文切换"。打字时，手在键盘上。需要 Bold → 抬手 → 鼠标移动到 B → 点击 → 手回到键盘。这 1-2 秒的打断，在写一篇 10 分钟的记录时发生 5-10 次。累积的"打断感"是文字编辑器最大的隐形体验成本。

Ctrl+B / Ctrl+I 解决了一部分。但 Ctrl+Shift+C（Callout / Code）没有被用户记住——没有 Slash Menu 时，用户只能点击工具栏。

---

## 4. Link 的 window.prompt 是否应该升级为 Popover

**应该。但不是因为 window.prompt 难看——是因为它打断了写作。**

Popover 的好处不只是"好看"。是它保持在编辑器上下文内——用户看到链接输入框出现在光标附近，而不是浏览器顶部弹出一个对话框。它不创建"跳出"的感觉。

但升级不是免费的——需要一个定位组件、输入状态管理、键盘导航（Enter 确认、Escape 取消）。约 50-80 行代码。

**优先级判断**：如果用户每个月插入 10 个链接，每次打断 2 秒，一个月 20 秒的打断。这是小数字。但累积一年，加上"这不像花园"的心理暗示，Popover 值得做。

**建议**：E3 级别。比 Strike 重要，比 Slash Menu 优先。

---

## 5. Slash Menu 解决的是"真实问题"还是"设计师的欲望"

**真实问题，但不是紧急问题。**

Slash Menu 解决的是"不离开键盘插入块"——这是真实的效率需求。但当前 8 种块类型，用户一次写作会话只用到 2-3 种。如果需要 H2，用户只需要抬手一次。如果需要 Callout，也是抬手一次。Slash Menu 把这些分散的抬手动作合并为一次 `/` 输入。

但问题是：**用户真的觉得"抬手点工具栏"是个问题吗？**

Google Docs 没有 Slash Menu。Apple Notes 没有。Bear 没有。它们都有工具栏，用户习惯了。

Slash Menu 的独特价值在块类型很多（20+）时体现——发现、搜索、快速选择。当前 8 种类型，用户都认识工具栏按钮的位置。Slash Menu 不会让体验从"差"变"好"，只会从"好"变"更好"。

**结论**：可以做，但不是现在。先修 Link popover。先让现有 8 种块体验完美。然后 Slash Menu 是锦上添花。

---

## 6. 当前项目最大的短板：功能缺失，还是内容为空

**内容为空。**

不是因为测试数据不够。而是因为"我的内容"不在里面。

50 条测试数据有标题、有摘要、有标签、有时间分布。但它不说话——它没有任何一条是"我真正经历的"。它不会让我在看到"来自花园"时愣住，不会让我在时间视图中找到那个特别的月份。

这不是技术问题。这是**产品的生命循环问题**：工具做好了，但花园还没有被真正种植。

**这个问题的解决方式不是开发新功能。** 用户需要的是时间——记录、积累、回顾、再记录。任何新功能都替代不了"使用"本身。

如果现在继续开发，我们是在为一个空花园建造更多工具。如果先种花（真实使用），花园自己会告诉你下一步需要什么。

---

## 7. 如果未来一个月只能做一件事

**修复 Link popover + Strike（1 行代码），然后停止开发。使用产品。**

理由：

1. Link popover 是当前唯一明显有"非花园感"的交互。修了它，编辑体验的显性断点全部消失。

2. Strike（删除线）是 StarterKit 自带功能，暴露它只需要 1 行工具栏代码。"我原来这么想，现在不了"——这是个人写作中常见的表达方式，值得有。

3. 然后停下来。不是因为开发累了，而是因为**没有使用数据的产品判断是盲目的**。现在做出的每一个决策（"Slash Menu 先还是 Task List 先"）都是基于想象，不是基于使用。

4. 1 个月后，带着真实使用体验回来。那时对 Slash Menu 的判断可能完全不同——也许发现工具栏真的没问题，也许发现 Callout 用得比预期多很多。真实的反馈比任何设计评审都准确。

---

## 总结

```
✅ 最可能坚持使用: 来自花园 > 时间视图 > 创建流程
⚠️ 使用频率可能很低: 类型聚合 > Blockquote
🔴 最打断写作流: Link window.prompt + 键盘↔鼠标切换
🟡 应该升级: Link popover（优先于 Slash Menu）
🟡 Slash Menu: 真实需求但非紧急
🔴 最大短板: 内容为空——需要真实使用，不是新功能
🎯 只做一件事: Link popover + Strike → 停止 → 使用
```
