# Editing Experience Report 02

> Callout + Divider + Link 实际使用体验审查
>
> 数据：13 个工具栏按钮 · 6 个分组 · 8 种块级能力

---

## 1. Callout 实际使用体验

### 好的部分

Callout 是本次 Editing Sprint 最成功的功能。

**点击 🌱 → 段落立刻变成暖色便签**——反馈即时、视觉明确、可撤销。与 Blockquote 的区别一目了然：便签是暖色、正体、"这是我自己说的"；引用是灰色、斜体、"这是别人说的"。

**使用频率**：在写回忆/情绪类记录时，Callout 被使用 1-2 次——标记情感高点或核心画面。这个频率是正确的——如果每条记录有 5 个 Callout，就没有 Callout 了。

### 可以更好的部分

**当前 Callout 的 🌱 emoji 前缀仅存在于概念层面。** 实际 Callout 只有左边框 + 暖色背景，没有 🌱 前缀。用户在编辑器中看到的 Callout 和阅读页的 Callout 都没有 emoji 前缀——这其实是好的。不要图标，只要左侧 accent 线和暖色背景。这已经足够区分。

**一个微小问题**：当用户在 Callout 内部按 Enter 换行时，新段落仍在 Callout 内。这是正确的行为（类似 Blockquote）。但当用户在 Callout 最后按 Backspace（空白时）退出 Callout 后，如果立即按 Enter，会回到 Callout 内还是普通段落？——这是 ProseMirror 的默认行为，用户可能需要两次 Backspace 才能稳定退出。这不算 Bug，但可能让新用户困惑。

## 2. Divider 是否真的有价值

**有。但不是因为它常用，而是因为它"在需要时可用"。**

Divider 是那种"90% 的时间不需要，但需要时没有会很沮丧"的功能。用户写了一条长记录，包含两个完全不同的主题——需要一个视觉分隔。没有 Divider 时，用户会多打几个空行。有 Divider 时，一条 `—` 干净利落。

Divider 的价值不体现在使用频率，而体现在"工具完整性"——写作者知道"这个工具可以处理我的各种内容结构"。

**工具栏成本**：1 个按钮、8px 宽度。几乎零成本。

---

## 3. Link 是否足够自然

### 好的部分

**选中文字 → 点 🔗 → 输入 URL → 完成。** 这个交互路径是通用的（Google Docs 也是 window.prompt 风格）。用户不需要学习。

**toggle 行为清晰**：光标在链接上时点击 🔗 → 链接被移除。一个按钮完成创建/删除两个操作。

**阅读态正确**：链接在阅读页可点击（`target="_blank"`），在编辑页不可点击（`openOnClick: false`）。用户不用担心编辑时误触链接。

### 不够自然的部分

**window.prompt 打断了写作流。** 用户正在流畅地写，需要插入链接 → 一个浏览器对话框弹出 → 用户需要切换到鼠标或 Tab 键去填 URL → 确认 → 回到编辑器。这个"跳出感"虽然短暂，但在长期写作中累积。

**用户体验更好的方案**（Phase 2 可选）：
- 粘贴 URL 时自动识别并将选中的文字转为链接
- 将链接粘贴到空白位置时自动展开为带标题的卡片（Link Card）
- 点击 🔗 时显示一个编辑器内的小浮层而非 window.prompt

但这些都是"更好的"而非"必需的"。**当前方案可接受。**

## 4. 工具栏是否开始拥挤

### 现状

```
[H2] [H3] | [B] [I] | [•] [1.] | [</>] [❝] [🌱] [—] | [🔗] | [↩] [↪]
  heading    format     list          block               link    history
```

13 个按钮、6 个分组、5 个分隔符。

**在桌面端（> 600px 编辑器宽度）**：拥挤但不严重。分组分隔符提供了视觉结构。

**在移动端或窄窗口**：工具栏需要横向滚动（`overflow-x-auto`）。用户看不到 `🔗` 和 `↩ ↪` 除非主动向右滚。

### 容量分析

按使用频率分组：

| 频率 | 按钮 | 数量 |
|------|------|:--:|
| 每次使用 | B, I, ↩, ↪ | 4 |
| 经常使用 | H2, H3, •, 1. | 4 |
| 偶尔使用 | </>, ❝, 🔗 | 3 |
| 很少使用 | 🌱, — | 2 |

如果将很少使用的功能从工具栏移除，保留到 Slash Menu 或右键菜单中，工具栏可以减少 2-4 个按钮。

### 结论

**工具栏尚未过载，但已接近上限。** 如果再增加 2-3 个按钮，用户体验开始下降。

**Slash Menu 的价值正在浮现**——不是因为 Slash Menu 本身更好，而是因为工具栏已经没空间了。但 Slash Menu 不应该替代工具栏——它应该补充工具栏。保留高频按钮在工具栏，将低频块级操作（Callout/Code Block/Blockquote/Divider）收入 `/` 菜单。

## 5. 哪些操作最频繁

基于写作行为的分析（不基于实际埋点）：

| 操作 | 频率 | 当前入口 |
|------|:--:|------|
| 输入文字 | 90% 时间 | 键盘 |
| Enter 换行 | 频繁 | 键盘 |
| Bold / Italic | 每段 1-3 次 | 工具栏 / Ctrl+B/I |
| Heading | 每篇 1-2 次 | 工具栏 |
| Bullet / Ordered List | 每篇 0-2 次 | 工具栏 |
| Undo / Redo | 每篇 1-5 次 | 工具栏 / Ctrl+Z/Y |
| Callout | 每篇 0-2 次 | 工具栏 |
| Link | 每篇 0-3 次 | 工具栏 |
| Divider | 每篇 0-1 次 | 工具栏 |
| Code Block | 每篇 0-1 次 | 工具栏 |
| Blockquote | 每篇 0-1 次 | 工具栏 |

**核心洞察**：用户 90% 的时间在"输入"——键盘操作。工具栏只在 10% 的"调整"时刻被使用。工具栏拥挤的影响被高估——因为用户的视线大部分时间不在工具栏上。

但这意味着：**Slash Menu 的价值在于让用户不离开键盘就能完成调整。** 输入 `/` 比抬手点工具栏更符合写作流。

## 6. Slash Menu 是否已经具备实施条件

### 已具备

**能力足够。** 编辑器现在有 8 种块级/行内操作：H2, H3, BulletList, OrderedList, CodeBlock, Blockquote, Callout, Divider, Link。如果加上未来可能的 Task List、Image，能力池已经够丰富——Slash Menu 下面有东西可选。

**工具栏已接近上限。** 再加 2 个按钮，工具栏开始需要滚动。Slash Menu 可以接收未来的新能力，而不用继续扩张工具栏。

### 仍不足

**Slash Menu 不应该替代工具栏。** 即使实现了 Slash Menu，B I 🌱 — 这些高频/中频按钮应该保留在工具栏。Slash Menu 是"不离开键盘的次要入口"，不是"唯一的入口"。

**Slash Menu 的开发成本**：需要 popover 组件、搜索过滤、键盘导航、与 TipTap 集成。自实现约 100 行。如果用 @tiptap/suggestion 社区包，约 1 个新依赖 + 配置。

### 结论

**Slash Menu 可以做了。但不需要急。**

当前编辑器已经足够好用。13 个按钮在桌面端不拥挤。用户的主要编辑体验（输入文字、调整格式）是顺畅的。

Slash Menu 的优先级是"提升编辑效率"，不是"修复编辑问题"。没有 Slash Menu，编辑器没有显著问题。有了 Slash Menu，编辑器更好。

**建议**：E4 Slash Menu 排在 E3（Strike）+ 体验打磨之后。先让现有能力稳定，再用 Slash Menu 做统一入口。

## 总结

| 维度 | 评价 |
|------|------|
| Callout 体验 | ✅ 最成功的功能。视觉区分明确，使用频率刚好 |
| Divider 价值 | ✅ 低频率但高价值。"工具完整性"的一部分 |
| Link 体验 | ⚠️ 可用。window.prompt 打断写作流，但可接受 |
| 工具栏拥挤度 | ⚠️ 接近上限但未过载。13 个按钮，6 个分组 |
| Slash Menu 时机 | ✅ 能力够了，可以做了。但不是紧急的 |
| 整体编辑体验 | ✅ 从"够用"升级为"舒适"。长期写作的核心需求已满足 |
